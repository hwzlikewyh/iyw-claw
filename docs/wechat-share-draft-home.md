# 微信分享进入首页草稿与发送修复

## 用户反馈与原因

Windows 接收器错误码 5 修复后，真实微信分享已在故障电脑交付了 ZIP、聊天正文和
附件索引。但导入提前调用 `create_chat_conversation`，再用 `openTab` 打开空的正式会话，
导致展示为会话详情页，而非用户要求的新会话首页。用户确认只有分享会话的回车和发送
按钮无反应，普通新建会话发送正常。

详情页的 `ConversationShell → ChatInput` 启用 `blockOfflineSend`，连接尚未就绪时
同时阻止回车和按钮发送；首页输入框复用正常新草稿的连接准备、排队和首次发送链路。
不能通过解除所有历史会话的发送限制来修复错误的导入入口。

## 验收与实现

1. 导入阶段只持久化输入内容，调用既有 `openChatModeTab` 打开独立的首页草稿，
   保持 `conversationId = null`、`folderId = 0`、`isChat = true`。
2. 为外部导入提供显式的独立草稿标识，重试聚焦同一页签；普通新会话和项目新会话
   不复用该页签，避免覆盖或重新定位用户正在编辑的分享内容。
3. 用户按回车或点击发送后，沿现有 `ConversationDetailPanel` 的 `createAndSend`
   流程创建隐藏聊天目录和数据库会话、绑定运行时并发送。没有新增发送入口或取消全局门禁。
4. v2 回执记录稳定草稿页签，覆盖连续批次、确认失败重试和重启恢复；草稿发送或清空后
   不因旧批次重放恢复。旧 v1 回执下仍存在、包含该批次引用的未发送内容可复制到首页，
   保留用户修改及原会话数据。

## 验证证据

- TypeScript 与改动文件 ESLint 通过。
- 一次性隔离运行实际 tab store、草稿存储和导入模块；平台网络调用替换为受控的输入，
  不发送真实消息、不读取用户数据，没有新增测试文件或运行仓库测试套件。
- 检查新导入仅调用 `native_share_prepare` 和 `native_share_complete`，没有创建数据库
  会话；两批独立草稿、原草稿保留、普通新会话不复用导入页签、重试不重复建页签均通过。
- 旧分享的编辑内容恢复、存储拒绝时不消费批次、确认失败后重试、已发送草稿不恢复、
  远程工作区拒绝本机交付的分支均通过。
- 前端 webpack 生产构建与 TypeScript 检查通过，静态导出 40 页。构建仍输出既有 PDF
  查看器依赖的服务端 `window` 引用提示，不影响本次导出；本次未改该依赖路径。
  没有修改 Rust、SDK 或依赖，不重跑已通过的原生编译。

旧会话的原始草稿作为恢复来源保留；v2 回执写入后不再重复读取旧来源，不删除已有
数据库会话。正常发送路径成功接收草稿后会清理对应草稿存储，阻止下次启动再次恢复。

这次改动在主应用前端中，需要包含本次提交的新版主程序；仅替换 0.1.326 接收器 EXE
不能改变旧版的会话界面与发送行为。真实微信转发后在首页按回车／点击发送的最终验收，
需要在故障电脑安装新版后进行，不能用上述隔离运行代替。
