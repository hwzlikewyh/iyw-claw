# 微信聊天记录原生导入

原助理接收用户从微信主动分享的聊天记录。微信中多选消息、合并转发、选择“原助理”，
接收完成后为每批分享打开“新建会话”首页，完整正文、原始文件和附件索引保存在
独立的未发送草稿中。按回车或点击发送后，才由正常首次发送流程创建正式会话并交给
模型处理。已有会话和未发送草稿不受影响。

消息渠道设置不再显示“聊天记录导入”区块，正常分享直接进入新会话草稿。
主应用导入失败时会打开恢复窗口，已接收的原批次保留，重试复用该批次的草稿页签。
恢复窗口中的“导入文件”可以选择微信已导出的 ZIP 或 TXT。
此能力不读取微信数据库，不监听聊天，也不自动发送微信消息。

## 平台与构建

| 平台 | 实现 | 范围 |
| --- | --- | --- |
| Windows | Rust/WinRT Share Target + 带外部位置的 MSIX 身份包 | Windows 10 2004（19041）及更新版本 |
| macOS | 内嵌 AppKit Share Extension + Rust 主应用 | 扩展目标 macOS 14+，Intel 和 Apple Silicon 分别构建 |
| 旧 Windows / Linux | 本地手动 ZIP/TXT 导入 | 不注册系统分享目标 |

共用代码位于 `src-tauri/share-core`；Windows 接收程序位于 `src-tauri/share-target`。
macOS 扩展位于 `src-tauri/native-share/macos`，仅完成系统文件表示接收和持久交接。
Tauri 主应用通过 `commands/native_share.rs` 操作本地收件箱，使用本机 transport，
不会把路径发送到远程服务器。首版只向本机会话交付；远程工作区显示明确提示。

正常桌面构建入口在 `prepare-sidecars.mjs` 中准备系统分享组件；Windows 分阶段发布
在 `finalize-staged-windows.mjs` 的签名阶段重新准备，确保接收 EXE 使用真实发布者身份，
不会因只搬运主程序和环境 helper 而漏包。可单独执行：

```powershell
node src-tauri/scripts/prepare-native-share.mjs --target x86_64-pc-windows-msvc
```

Windows 复用既有 `IYW_CLAW_SIGN_*` 签名设置，从现有证书获取 MSIX Publisher。
Azure 等无法自动取得证书 Subject 的方式，使用 `IYW_SHARE_PUBLISHER`，其值必须
与真实签名证书完全一致。构建需要 Windows SDK 的 `makepri.exe`、`makeappx.exe`
和 `signtool.exe`。校验还使用 SDK 的 `mt.exe` 读取最终 EXE 清单。接收程序含嵌入的
MSIX 身份和图标，不依赖 .NET。清单以 UTF-8 文件嵌入，支持中文证书发布者。
MSIX 必须在同一次签名操作中完成 RFC3161 时间戳；硬件 token 签名使用微软的
`SignerSignEx2` 与 `APPX_SIP_CLIENT_DATA`，EXE 保留既有分阶段签名流程。

无签名构建仅生成接收程序，不发布可注册的 MSIX；不会创建自签名证书或修改信任库。
手动导入仍可用。`--no-sign` 构建会明确切换为这种行为，避免打包旧的签名制品。

macOS 复用 `APPLE_SIGNING_IDENTITY`、`APPLE_TEAM_ID`。正式签名采用
`<TEAM_ID>.app.iywclaw.share` App Group，主应用和扩展共用同一标识。
扩展先签名，再通过 Tauri `bundle.macOS.files` 放入主应用 `Contents/PlugIns`，
随主应用签名、公证。无签名本地构建使用受限共享目录。
本次不提高主应用现有 13.5 最低系统版本；13.5 不承诺该扩展可用。

安装 Windows 正式包后，安装器尝试为当前用户注册分享入口；注册失败保留正常安装，
应用启动还会检查当前用户的注册状态，缺失时尝试补齐。用户可在导入恢复
窗口点击“启用系统分享”重试。安装检查等待 GUI 接收器退出，再核对包名、发布者和
AUMID，不依赖 PowerShell 对 GUI 程序的旧退出码。更新使用包版本维护入口，卸载先移除
属于当前安装路径的身份包。用户选择保留数据时保留聊天归档，彻底删除时清理本机
收件箱。macOS 查询 pluginkit 的实际启用状态，为新安装扩展注册并启用；尊重用户主动
关闭及系统禁用状态，可在系统的共享扩展设置中重新启用。来源应用菜单可能需要重启后刷新。

系统分享注册只覆盖消费系统扩展的应用，不等于所有聊天软件都会显示该入口。
企业微信的 WorkBuddy 菜单是专用集成；飞书“消息快捷操作”和钉钉“酷应用消息菜单”
需要独立的开放平台应用配置、鉴权和发布，不能靠本地注册代替。能力依据与本次核查
见 [分享修复记录](native-share-followup.md)。

## 文件与恢复

Windows 和无签名 macOS：用户本机应用数据目录下的 `app.iywclaw/share-inbox`。
正式 macOS：App Group 容器下的 `share-inbox`。

```text
share-inbox/
  Staging/<uuid>/          接收中的批次，尚未对主应用可见
  Ready/<uuid>/
    manifest.json         schemaVersion=1，UTC 时间，原始相对路径和字节数
    files/                已接收的原始文件
    derived/              解析正文、媒体副本、附件索引和准备状态
    imported.json         确认写入会话草稿后的标记
```

复制完全部文件并同步后，先关闭清单文件句柄，再将整批原子移动至 Ready；系统成功
回执发生在提交之后。Windows 在目录内仍有打开的文件时会拒绝移动目录，返回错误码 5。
通知仅用于唤醒，启动和手动打开窗口都会重新读取持久批次。应用崩溃不会消费
待处理批次；中断的解析重新生成派生文件，进程间文件锁避免同时重建同一批次。
导入后不移动原文件，保持草稿中的路径稳定，也不自动删除仍可能被会话引用的记录。

草稿导入使用一组内联引用写入首页草稿。localStorage 的 v2 回执保存批次对应的草稿
页签标识，不在导入阶段创建数据库会话或隐藏目录；目录与会话复用既有新会话生命周期。
草稿持久化成功后才挂载输入框并回写已导入标记，避免冷启动时输入框未就绪丢失内容。
确认标记失败后重试会复用同一页签，不重复追加已保存的批次，也不恢复已发送或清空的
旧草稿。重启时可恢复尚未发送的分享草稿；普通“新建会话”不会复用这些独立导入页签。
旧 v1 回执仍有本地未发送内容时，将内容及用户编辑复制到首页草稿，保留旧会话数据；
不存在草稿或已经发送的旧批次不会自动重新导入。
“已加入草稿”不表示已发送给 Agent。发送给云端模型仍遵循原助理现有模型链路。

单次最多 32 个文件，原始文件及整批各限制 512 MiB；整批归档最多 1000 个条目，
总展开量最多 1 GiB，正文合计最多 16 MiB。ZIP 路径、链接、压缩格式、CRC、字节数
均在处理链路中检查。媒体按编号隔离到派生目录，不使用 ZIP 内部路径写出文件。
未知 TXT 格式保留原文并给出警告，不伪造发送人或条数。预览最多显示 40000 个字符。

## 验证边界

按仓库约定不新增或运行测试套件。错误码 5 已在开发机和用户故障电脑用相同文件操作
复现，并对修复后的实际归档库执行复制、提交、解析、引用和回执检查。
编译、类型检查、lint、打包语法及静态调用链检查
结果记录在交付说明。构建门禁核验 EXE 嵌入身份与 MSIX 一致、PRI 和图标内外哈希一致、
双签名有效；安装制品校验也要求这些资源存在。系统身份检查成功不能替代真实微信菜单
及聊天 ZIP 转发验收。macOS Developer ID/App Group 权限和双架构实机流程仍需验证。
