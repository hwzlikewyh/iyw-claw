# Windows 安装器自动覆盖与进程清理容错设计

## 背景

Windows 安装器在覆盖安装和卸载前生成 PowerShell 脚本，查询当前用户且位于
安装目录内的 `iyw-claw.exe`、`agent-browser.exe` 和旧 MCP 进程。现有脚本同时
要求 CIM 的 `ExecutablePath` 与 `Get-Process.Path` 可用并完全一致。

Windows 可能对仍存活的后台进程返回空的 `Get-Process.Path`。当前实现将这种情况
作为整个查询失败，返回错误码 `2`。安装器因此无法停止已确认位于安装目录的进程，
覆盖安装中止或退回 Tauri 的“已安装”选择页，用户需要手工选择卸载并重试。

## 目标

- 同一安装根目录已有版本时，普通双击安装器自动进入被动覆盖更新，不展示
  “安装前卸载 / 请勿卸载”选择页。
- 自动停止当前用户、当前安装目录中的主进程和已确认的辅助进程。
- `Get-Process.Path` 不可用时仍可使用 CIM 提供的规范化可执行路径完成身份确认。
- 无法确认辅助进程身份时跳过该进程并记录原因，不阻断整个安装。
- 无法确认或停止主进程时继续 fail-closed，不替换正在使用的应用目录。
- 保留测试模式、应用内 updater、安装事务回滚和用户数据保留语义。
- 本地 `runtime` 与 Codex 私有目录的版本、入口、平台和 marker 完整时，启动只做
  隐形快速校验，不显示准备进度条、不下载、不重复安装。

## 方案比较

### 方案 A：仅移除 `Get-Process.Path` 校验

实现最小，但会降低所有进程的 PID 复用与身份变化防护，主进程安全边界过宽。

### 方案 B：CIM 为主，主进程严格失败，辅助进程容错

使用 CIM 的 `ExecutablePath`、进程所有者 SID、PID、创建时间、文件名和安装目录
作为稳定身份。`Get-Process.Path` 可用时作为额外交叉校验，不可用时不再单独失败。
主进程的身份、范围或停止动作失败时阻断安装；辅助进程无法确认时记录并跳过。

这是采用方案。它解决实际兼容问题，同时保留覆盖安装最关键的主进程保护。

### 方案 C：按进程名直接强制终止

用户操作最少，但可能终止其他安装目录或其他登录会话中的同名进程，不接受。

## 详细设计

### 进程身份

`installer-process-control.nsh` 生成的 PowerShell 脚本以 CIM 记录为主来源：

1. 读取进程所有者 SID、`ExecutablePath`、PID、创建时间和进程名。
2. 规范化真实路径并拒绝符号链接或 junction 路径。
3. 验证文件名、当前用户 SID 和安装目录完全匹配。
4. 尝试读取 `Get-Process` 的运行时对象和路径。路径可用时必须与 CIM 路径一致；
   路径为空时继续使用已验证的 CIM 路径。
5. 停止前再次读取 CIM 记录，比较 PID、创建时间、所有者、路径和进程名，防止
   PID 复用或进程身份变化。

主进程 `iyw-claw.exe` 的任一关键身份读取或二次确认失败都返回查询失败。辅助进程
`agent-browser.exe` 和旧 MCP 进程的身份无法确认时输出明确的跳过日志并继续扫描。
已经确认属于当前用户和安装目录的辅助进程如果停止失败，仍然返回失败，避免带锁
文件进入替换事务。

### 自动覆盖更新

`installer-hooks.nsh` 在 GUI 初始化时读取 `InstallRoot`。普通交互安装存在有效安装根
时，安装器以固定参数重新启动自身：

- 应用未运行：`/P /UPDATE`
- 应用正在运行：`/P /R /UPDATE /ARGS --restore-installer-session`

重新启动的进程复用现有安装目录，自动进入覆盖更新并在需要时恢复应用页面。测试
模式不查询生产进程或注册表隔离键；已经携带 `/UPDATE` 的应用内 updater 不重复
启动；新安装仍显示正常安装界面和目录选择。

### 错误处理

- 安装根或主进程状态无法确认：中止更新，旧版本不变。
- 已确认的进程无法停止：中止更新，旧版本不变。
- 单个辅助进程缺少可验证身份：记录进程名、PID 和脱敏原因后跳过；不记录命令行、
  用户路径之外的载荷或凭据。
- 安装事务开始后的写入失败：沿用现有应用目录事务回滚。
- 静默和被动模式不弹窗，以非零退出码交给 updater；交互模式只对真正阻断安装的
  主进程或事务错误弹窗。

### 启动快速路径与软件内更新

启动门禁保持 `checking` 隐形状态，只有收到真实 runtime 下载/解压进度事件才进入
可见准备对话框。`runtime_bootstrap` 的 `already_installed` 分支和 Codex 本地目录
完整性校验均在该隐形阶段完成；Node/Git/uv 与 Codex 都已就绪时直接挂载工作区。

软件内更新继续使用现有 Tauri updater 到 NSIS `/UPDATE` 的链路：更新前由安装器按
同一进程身份规则停止当前用户、同安装目录进程，应用事务只替换 `app`，更新后恢复
窗口参数并重新运行隐形快速校验。`runtime`、Codex 私有目录、配置、数据、Skills、
Agent 和日志目录不随 app 替换删除；只有校验失败或版本缺失时才显示准备进度并执行
版本中心安装。

## 验证

仓库默认不执行完整桌面构建。本次执行以下定向验证：

- 静态检查 NSIS 栈参数、分支标签、返回码和安装/卸载前调用链。
- 从 NSIS 生成内容中提取 PowerShell 脚本并执行语法解析。
- 模拟 `Get-Process.Path` 为空但 CIM 路径有效，确认主进程仍能被识别和停止。
- 模拟辅助进程身份不可读，确认输出跳过日志且不返回全局查询失败。
- 模拟主进程 CIM 路径、所有者或安装目录不匹配，确认 fail-closed。
- 检查普通已有安装自动转入 `/P /UPDATE`，测试模式和已有 `/UPDATE` 不递归启动。
- 模拟 Node/Git/uv 与 Codex 目录均已就绪，确认启动门禁不显示进度条；模拟任一组件
  缺失，确认只有真实安装 progress 事件出现后才显示进度条。
- 检查软件内更新前后 `app` 替换、受管目录保留、窗口恢复和启动快速路径的调用顺序。
- `git diff --check` 和人工审查安装事务、用户数据保留、测试隔离逻辑。

GitHub Actions 的 Windows x64/x86 构建继续负责真实 NSIS 生成、安装后 sidecar 与
runtime seed smoke。新版本仅在两种 Windows job 和其余发布矩阵全部成功后公开并同步
到 Fusion。
