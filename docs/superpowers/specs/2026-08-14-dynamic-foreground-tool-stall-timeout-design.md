# 前台工具动态卡死超时设计

## 背景

ACP 提示卡死检测目前只看 `SessionState.last_agent_event_at`。连接处于
`Prompting` 且连续 600 秒没有 Agent 事件时，后台扫描会发送错误并取消整轮提示。
这能终止真正挂起的模型流，但也会误杀正常的静默前台工具：例如
`shell_command` 声明 `timeout_ms = 1_200_000` 允许运行 20 分钟，渲染过程没有输出
ACP 事件时仍会在第 10 分钟被取消。

`SessionState.active_tool_calls` 已保存工具状态和结构化 `input`，其中
`shell_command` 的输入包含 `timeout_ms`。因此可以在不修改 ACP 协议、数据库和
前端的情况下，根据当前活动工具计算本轮有效卡死阈值。

## 目标

- 普通模型等待继续使用现有可配置的提示卡死阈值，默认 10 分钟。
- 前台工具运行时，根据工具声明的 `timeout_ms` 动态延长卡死窗口。
- 工具结束后立即恢复普通提示卡死规则。
- 保留绝对安全上限，避免损坏或恶意输入让会话无限运行。
- 不自动重试整轮提示，避免重复执行渲染、写文件等有副作用的操作。
- 日志能够说明实际采用的阈值，但不记录命令内容或完整工具输入。

## 非目标

- 不修改模型客户端已有的网络重试策略。
- 不新增前端设置、状态字段或错误类型。
- 不改变后台任务、权限请求和用户问答已有的卡死豁免逻辑。
- 不保证被操作系统、Agent 或用户取消的工具自动恢复。
- 不修改各工具自己的执行超时。

## 方案比较

### 方案一：活动前台工具永久豁免

只要存在 `Pending` 或 `InProgress` 工具就跳过卡死检测。实现最简单，但真正挂死
的工具会让连接永久停留在生成中，失去现有 watchdog 的安全价值，因此不采用。

### 方案二：所有前台工具使用固定 30 分钟阈值

比当前 10 分钟更适合渲染，但无法尊重工具已经声明的超时；短任务需要等待过久
才能恢复，超过 30 分钟的合法任务仍会被提前取消，因此不采用。

### 方案三：按工具声明动态计算，带回退和上限

从活动工具输入读取 `timeout_ms`，加宽限后限制在安全范围内。缺少声明时使用固定
回退值。该方案能覆盖本次 20 分钟渲染，同时继续终止真正挂起的任务，因此采用。

## 动态阈值规则

新增独立的后端策略函数，根据基础阈值和当前 `active_tool_calls` 返回绝对截止时间
和诊断信息。

活动前台工具定义为状态为 `Pending` 或 `InProgress` 的工具。`Completed` 和
`Failed` 工具仍保留在 turn 状态中，但不参与延长。

常量：

- 工具超时宽限：60 秒。
- 缺少或无法解析 `timeout_ms` 时的前台工具回退阈值：30 分钟。
- 工具派生阈值的安全上限：60 分钟。
- 工具运行时起点：第一次观察到该工具为 `Pending` 或 `InProgress` 的时间；后续
  `ToolCallUpdate` 不重置起点。

单个活动工具的绝对截止时间计算：

1. 若顶层 `input.timeout_ms` 是正整数，将毫秒向上取整为秒后加 60 秒宽限，得到
   工具窗口。
2. 将工具窗口限制为不高于 60 分钟；操作者配置的基础阈值不受该上限影响。
3. 若缺少、为零、为负数、不是整数或发生数值溢出，使用 30 分钟回退窗口。
4. 工具截止时间为 `started_at + 工具窗口`。基础截止时间为
   `last_agent_event_at + 基础阈值`。
5. 最终截止时间取基础截止时间和所有活动工具截止时间的最大值。这样工具有持续
   进度事件时不会被误杀，工具长期静默时仍会在自己的声明窗口后被取消。
6. 操作者通过环境变量设置的基础阈值高于 60 分钟时不得被缩短；60 分钟上限只
   限制工具带来的额外延长。

存在多个活动工具时取最晚工具截止时间。没有活动前台工具时直接返回基础截止
时间。

示例：

- 基础 600 秒，工具 13:47:36 开始，`timeout_ms = 1_200_000`：工具截止时间为
  14:08:36（含 60 秒宽限）。
- 基础 600 秒，`timeout_ms = 60_000`：工具截止时间不会早于基础截止时间。
- 基础 600 秒，工具没有 `timeout_ms`：从 `started_at` 起使用 30 分钟回退窗口。
- 基础 7,200 秒：最终截止时间不会早于基础截止时间。

## 数据流

1. Agent 发送 `ToolCall` 或 `ToolCallUpdate`。
2. `SessionState::apply_event` 更新 `active_tool_calls`，首次进入活动状态时记录
   运行时 `started_at`，并刷新 `last_agent_event_at`。
3. 定时扫描读取连接状态，先保留权限、问答和后台工作现有豁免。
4. 策略函数检查非终态前台工具并计算有效阈值。
5. 当前时间达到最终绝对截止时间时才成为取消候选。
6. 工具的终态事件刷新 `last_agent_event_at`；下一轮扫描不再看到活动工具，恢复
   基础阈值。

若工具产生输出或状态更新，现有事件应用路径自然刷新活动时间，不需要额外心跳
协议。

## 代码边界

- 新增一个小型 `acp` 内部模块，封装活动工具识别、运行时起点、`timeout_ms` 解析
  和绝对截止时间计算。
- `ConnectionManager::sweep_stalled_prompts` 只消费策略结果，不承担 JSON 解析。
- 只给 `ToolCallState` 增加跳过序列化的运行时 `started_at`，不修改 ACP 事件和
  前端序列化结构。
- 保持现有 `prompt_stall_timeout` 错误码和取消流程，降低行为面变化。

## 错误与日志

取消日志和错误消息使用本次实际生效的绝对截止时间，而不是全局基础阈值。结构化
日志增加：

- `effective_timeout_secs`
- `active_foreground_tools`
- `timeout_source`：`base`、`declared` 或 `fallback`
- `longest_tool_runtime_secs`

不记录工具名称、命令、完整输入、工作目录或凭据。前端继续通过现有错误分类显示
超时提示。

## 边界与安全

- 使用饱和运算处理毫秒转秒、宽限相加和起点加窗口，异常输入不能溢出。
- 只读取顶层数字 `timeout_ms`，不递归扫描任意 JSON，也不根据工具标签猜测。
- 工具输入尚未拼接完成时使用 30 分钟回退；后续输入更新会刷新事件时间并采用
  声明值，但不会重置 `started_at`。
- 环境变量将提示卡死检测设为 `0` 时，现有扫描整体禁用行为保持不变。
- 不自动重放用户消息或工具调用；取消后由用户或 Agent 在检查产物后决定是否恢复。
