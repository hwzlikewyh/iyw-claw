# 提问超时后的聊天渠道补问设计

## 目标

当 `ask_user_question` 等待用户回答超过现有上限时，让原助理明确知道这是“等待超时”，并在当前回合具备聊天渠道上下文时尝试通过原渠道发出一次文字补问。用户可以在渠道中回复，回复进入现有渠道会话的下一轮，由原助理继续处理。

## 范围

- 只对已有聊天渠道上下文的会话提供补问建议；渠道目标继续由宿主绑定。
- 保留现有 600 秒问答等待上限、问题卡片清理和连接取消行为。
- 区分用户主动跳过、问答取消和等待超时，至少让 Agent 能识别超时。
- 超时后由原助理决定是否调用当前渠道发送能力，宿主不代发第二条问题。
- 超时补问使用普通文字，让用户直接回复；不新增第二个交互卡片或跨进程待回答状态。

不在本次范围内：为桌面会话寻找任意已配置渠道、改变渠道路由或收件人、延长问答等待、把渠道回复自动绑定成原问题的结构化答案、增加新的持久化表。

## 方案选择

### 方案 A：超时信号加原助理补问（采用）

监听器在超时时清理 pending question，并在工具结果中增加稳定的超时状态。工具结果同时给出宿主能力提示：如果当前回合有渠道上下文，调用当前渠道发送能力发出一次简短补问，然后结束本轮。用户回复后沿用现有聊天渠道新回合和会话历史。

优点是改动集中在已有问答协议和工具渲染，渠道身份仍由现有上下文保护，问题措辞由最了解任务的原助理生成。缺点是模型可能选择不补问，或者渠道发送能力不可用时只能回到原会话。

### 方案 B：宿主超时后自动代发

宿主在监听器超时分支直接把原问题转换为渠道消息，并保存一个待回答状态。

这样补问触达率较高，但宿主无法可靠地压缩复杂表单、判断敏感内容或决定是否继续，且必须新增回复关联、过期、重启恢复和重复发送处理。它也会和原助理收到超时结果后的主动回复竞争，不采用。

### 方案 C：只延长或重试原交互卡片

延长 600 秒或超时后重新注册同一问题卡片。

这会继续占用 Agent 的阻塞回合，无法覆盖 Agent/连接已取消的情况，也会让用户看到重复卡片，不采用。

## 协议与数据流

1. `DelegationListener::wait_for_ask` 在回答、取消和超时之间选择。超时分支仍调用 `cancel_question`，保证原卡片在所有客户端清理。
2. `ask_user_question` 的 broker 结果扩展为可选稳定字段：

   ```json
   {
     "answers": [],
     "declined": true,
     "status": "timed_out",
     "fallback": "current_channel"
   }
   ```

   正常回答使用 `status: "answered"`，用户跳过使用 `status: "declined"`，宿主撤销 pending waiter 但仍能写回结果时使用 `status: "canceled"`。对端主动断开时本来就没有可写回的工具结果；注册失败继续返回原有交互不可用错误，不能伪造用户回答。
3. companion 的 `render_ask_result` 对 `status: "timed_out"` 输出明确的 Agent-facing 文本：超时不代表同意或拒绝；有当前聊天渠道能力时，使用当前绑定目标发一条简短文字补问并结束本轮，等待用户下一条消息；没有该能力时，说明需要用户回到原会话处理。结果保持 `isError: false`，因为这是可处理的交互状态。
4. 原助理使用已有当前渠道发送能力。发送结果沿现有渠道工具审计和投递回执处理；不新增宿主侧发送入口。用户回复进入现有 `SessionBridge` 路由，正常带入同一会话历史。
5. 前端历史结果解析保留 `status`，问答结果卡把超时显示为“等待超时”，避免把它错误显示为用户主动忽略。旧结果没有 `status` 时按现有 `declined` 兼容显示。

## 组件改动边界

- `src-tauri/src/acp/delegation/listener.rs`：为超时结果添加状态字段，保持清理顺序和日志字段；回答/取消结果继续兼容旧客户端。
- `src-tauri/src/acp/delegation/companion.rs`：渲染超时的 Agent-facing 指令和结构化字段；不让超时被当成普通 declined。
- `src-tauri/src/acp/delegation/transport.rs`：更新 broker 注释和结果契约说明。
- `src-tauri/src/acp/delegation/tool_schema.json`：说明超时是独立状态，当前渠道会话可用时允许补问。
- `src/lib/ask-question.ts`、历史问答结果组件和对应中英文消息：解析并展示可选 `status`，兼容旧 transcript。

不修改 `QuestionOutcome` 的用户答案模型，也不把渠道身份、目标 ID 或凭据放进问答结果；渠道发送仍通过既有认证和上下文校验。

## 错误处理与并发

- 超时时先撤销 pending question，再写出超时结果；任何迟到的按钮、文字回答都按“问题已结束”处理。
- 超时结果不触发自动重试，避免重复发送和重复执行副作用。
- 当前渠道能力缺失、上下文过期或发送失败时，原助理收到明确失败结果并回到原会话提示；不会伪造“已送达”。
- 发送内容不得包含秘密字段值。含密码字段的问题继续要求在原会话填写，补问指令只允许提示用户回到原会话。
- 日志记录 `connection_id`、`question_id`、状态、等待时长和失败类别；不记录完整问题正文、答案、令牌或凭据。

## 验证

1. Rust 定向验证 broker 结果：回答、主动跳过、超时、连接取消分别得到预期状态；超时仍发出 question-resolved 清理事件。
2. companion 定向验证：超时结果的 `content` 明确要求当前渠道补问，普通 declined 不触发该指令，`isError` 保持为 false。
3. TypeScript 定向验证历史结果解析和展示：带 `status: "timed_out"` 显示等待超时；缺失 status 的旧结果保持原有显示。
4. 静态检查聊天渠道调用链，确认补问使用当前绑定目标，不能从超时结果注入任意目标或绕过渠道工具审计。
5. 按仓库约定完成静态逻辑审查；默认不运行测试命令，除非实现阶段用户另行要求。

## 验收标准

- `ask_user_question` 等待 600 秒无回答后，原卡片被清理，Agent 收到可识别的 `timed_out` 结果。
- 原助理在聊天渠道会话中能根据该结果调用当前渠道发送能力，向原用户发出一次文字补问，并不把超时当成用户选择。
- 用户的渠道回复进入同一原助理会话，后续处理沿用现有消息路由和历史。
- 用户主动跳过、宿主撤销和超时在可写回的 Agent-facing 结果及历史卡片上可区分；对端主动断开仍没有工具结果，旧 transcript 不回归。
- 渠道不可用、上下文失效、敏感问题和迟到回答均有明确失败/回退行为，不产生重复发送或虚假成功。
